# CrewLane - Decision Log

Binding record of the 2026-08-17 ground-up rethink. Baseline process model:
[Teaching Agile SDLC](https://teachingagile.com/sdlc/). Rule of the log (D1):
the baseline is the default; every deviation is deliberate, recorded, and has a
return path. The readable companion is `docs/crewlane-rethink.html`.

## Product and entry

- **D1 - Ground rules.** Clean slate; a proper SDLC system as baseline; every deviation deliberate and recorded; leverage AI to maximum capability; validate choices with live research.
- **D2 - Entry.** The domain loads straight into the app. No marketing or landing page; the audience is people directed to use it.
- **D3 - Wall first.** Sign-in wall before anything; nothing about the product is visible pre-auth. No VPN double-walling; TLS is automatic at the hosts.
- **D4 - Access policy.** Completing sign-in is the only gate; one sign-in method. Recorded consequence: the app URL is effectively semi-public up to the wall.
- **D5 - Accounts.** Just-in-time: first successful sign-in creates the account. Nothing pre-provisioned.
- **D6 - Stored identity.** Display name, email, provider ID. Nothing else.
- **D7 - Auth provider.** Stytch (Consumer), implementing D3-D6 as specced. *Superseded for v1 by D42/D44.*
- **D8 - First landing.** Zero projects sends you straight to project creation; the project list becomes home once a project exists.
- **D9 - Creation.** One free-text box ("What are you building?"), framed on the baseline's business-need step. Project name is derived from the text.

## Experience and intake

- **D10 - UI paradigm.** Persistent chat spine + structured workspace (Claude-web dual-surface pattern). No wizard flows; gates and acceptance are first-class UI, never chat bubbles.
- **D11 - Agent-UI protocol.** AG-UI as transport (via CopilotKit); generative UI through A2UI's trusted-catalog model - the agent picks from our widget registry (question card, coverage meter, conflict card, acceptance panel). The React-renderer spike is the validation gate for this bet.
- **D12 - Frontend.** Next.js App Router, TypeScript, Tailwind CSS.
- **D13 - v1 input.** Free text + document upload (supported formats, honest failures) + audio upload with our own Whisper transcription. Email-in deferred; native Teams connector deferred behind tenant-admin consent. One ingestion pipeline: capture with dual provenance (submitter is not necessarily the speaker) -> normalize -> extract candidate facts -> belief layer (duplicates merge as corroboration; conflicts go to a human review queue; nothing silently overwritten).
- **D14 - Any project.** v1 accepts new or in-flight, greenfield or brownfield, as long as evidence arrives through the input channels. One mechanism serves all four.
- **D15 - Read-back first.** The AI's first move is a mirror: known-with-source vs not-stated; the user corrects and confirms. The same mechanism doubles as a lifecycle assessment for in-flight projects.
- **D16 - Question delivery.** Agent-chosen per moment, defaulting to small batches of purpose-labeled question cards, each with an explicit "I don't know / not applicable" option.

## Knowledge model and process engine

- **D17 - Living model.** The project model is the product; documents (Charter, SRS, any phase artifact) are rendered, timestamped views of it. Acceptance binds to immutable snapshots.
- **D18 - Process as template.** Phases, coverage areas, gate rules, and view templates are versioned data the engine consumes; projects pin a template version. v1 ships one default template and no editing UI.
- **D19 - Planning coverage.** The baseline's 8 areas as backbone, tiered, with the AI allowed to propose extra areas. Trimmed for v1 by deviation 1 and D24: four core areas (business need & vision, scope & exclusions, stakeholders, risks) plus optional feasibility.
- **D20 - Planning gate.** Hard: a specific Charter snapshot must be explicitly accepted before Requirements begins.
- **D21 - Who accepts.** Anyone in the project. Acceptance is recorded accountability (name + timestamp + snapshot ID), not a role permission.
- **D22 - Cards and strings (locked).** Typed knowledge graph: 15 card types (source/evidence, business need, actor, use case, requirement, constraint, assumption, data entity, interface, story, risk, stakeholder, decision, open question, glossary term) and exactly 4 edge types (`supported-by`, `derived-from`, `depends-on`, `conflicts-with`). Fields for structure, strings for the web; no untyped related-to edges, ever. Card status: candidate -> confirmed -> accepted.
- **D23 - Agent framework.** LangGraph. Gates map naturally to durable interrupts.
- **D24 - Feasibility.** Fully optional in v1 - offered as grounded, cited research with recommendations, never gating. Deviation from the baseline's go/no-go center, recorded with reasons and a template-row return path.
- **D25 - Requirements gate.** One hard gate: explicit acceptance of the SRS snapshot completes the phase.
- **D26 - Jira.** Out of scope until after the Design phase is designed.
- **D27 - Seeded handoff.** Requirements starts by consuming the accepted Charter (scope becomes product boundary, stakeholders become actor candidates); inherited ground is never re-asked.

## Stack

- **D28 - Inference.** Groq free tier only (LLM + Whisper); model-agnostic via config. No local GPU / Ollama.
- **D29 - Backend.** FastAPI (Python), which settles LangGraph on Python. Architecture: Next.js frontend + FastAPI/LangGraph backend.
- **D30 - Store.** Postgres for the card/string model.
- **D31 - Web search.** Decided at grounding time; SerpAPI, Tavily, and Brave-class options compared on free quotas.
- **D32 - Jobs.** Postgres-backed job queue with the worker loop in-process with the API. Upgrade path: ARQ + Redis.
- **D33 - Database hosting.** Neon (auto-resume ~500 ms, pgvector included).
- **D34 - Object storage.** Cloudflare R2 behind a small storage port (S3 API); swapping is config.
- **D35 - ORM/migrations.** SQLAlchemy + Alembic, migrations from commit one.
- **D36 - Agent persistence.** LangGraph's Postgres checkpointer - gates are durable; a paused graph survives restarts.
- **D37 - FE-BE contract.** FastAPI's OpenAPI schema generates the TypeScript client in CI; drift between Python and TS becomes a build failure.
- **D38 - Auth verification.** Stytch session verified in FastAPI middleware on every request; frontend uses the Stytch Next.js SDK. *Superseded for v1 by D42.*
- **D39 - Parsing/transcription.** PyMuPDF (pdf), python-docx, openpyxl; images via Groq vision models; audio chunked with ffmpeg before Groq Whisper (its per-file upload cap means long recordings are split - known, handled).
- **D40 - Repo and deploy shape.** Monorepo (`frontend/` + `backend/`); docker-compose for local Postgres + pgvector; hosting Vercel (Next.js) + Render (FastAPI), both free. Recorded caveat: Render free services sleep after ~15 idle minutes (~1 min cold start) - acceptable for internal v1.
- **D41 - Portability.** No vendor-exclusive features, ever: no Vercel-only APIs, no Neon-only features, no R2-only behaviors. Each host is used strictly as "a place that runs containers / vanilla Postgres / the S3 API"; on-prem migration is compose up + pg_dump + object sync + env vars. Original caveat (Stytch as the one cloud dependency without a self-host path) is deferred with D44 — v1 auth is a signed cookie, fully self-contained.

## Addendum - retrieval scope (post-D41, same rethink)

pgvector over cards and evidence chunks powers: belief-layer duplicate/conflict
detection, evidence-grounded chat with citations, "do the uploads already answer
this" coverage checks, evidence-on-hover in rendered documents, and (later,
opt-in) cross-project memory. Embeddings via a free-tier API, picked at wiring
time (Gemini is the candidate). RAG is never used for deterministic logic:
gates, document rendering, and audit are plain code over typed data.

## Agents lane (2026-08-18)

Recorded while designing the orchestration layer; extends the Phase 1 updates.

- **D45 - Graph shape.** One generic phase-runner graph per phase per project (thread_id = `<project_id>:<phase>`); phase templates are data fed to the same graph (D18 upheld). Gates are the graph's final `interrupt()` - D23/D36 upheld. Return path considered and recorded: per-turn stateless invocations if long-lived threads prove painful.
- **D46 - Single lane.** Every user message resumes the phase thread; the graph routes answer vs aside itself. No separate chat path.
- **D47 - Inline extraction.** Interview answers are extracted to candidate facts inside the turn, so the next question always knows what was just said. Uploads stay on the job queue (D13).
- **D48 - Transport.** AG-UI/CopilotKit + A2UI widgets are the target from the first agents work; the graph is transport-agnostic (all output lands as message rows), so the REST endpoints serve today and the AG-UI stream mounts on top without touching the graph. Fallback if the A2UI renderer fails its spike: keep the widget dicts over REST.
- **Interim seams (temporary, by design):** extracted facts persist as `fact_log` widgets on the chat spine until the storage lane implements the cards model behind `KnowledgePort`; `ScriptedInference` stands in whenever `GROQ_API_KEY` is unset so the app stays runnable; the acceptance panel shows a digest until the deterministic view renderer exists.

## Workspace / widget lane (2026-08-18)

Recorded with `feat/5-workspace-gates`; implements the D48 REST fallback.

- **D49 - Checkpointer startup.** `PostgresSaver.setup()` runs once in app lifespan (`init_checkpointer()`), not on the first user request. Reason: setup uses `CREATE INDEX CONCURRENTLY`, which deadlocks when concurrent SQLAlchemy request sessions hold open transactions — observed as a blank project page. Tests use in-memory sqlite and skip this path.
- **D50 - REST widget catalog.** Five trusted widgets rendered from `messages.widget` over REST: `question_card`, `coverage_meter`, `fact_log`, `acceptance_panel`, `gate_accepted`. Gates and coverage live in the **workspace** panel (D10), not chat bubbles. `POST /projects/{id}/gate` wires accept/revise. Question cards are **open-ended** (D16): free-text answer + explicit N/A — not multiple choice. AG-UI/A2UI streaming remains the D48 upgrade path on top of the same widget JSON.

## Cards & snapshots lane (2026-08-18)

Recorded with `feat/6-cards-snapshots`; replaces the interim `fact_log`-only storage (D46) with real Postgres tables behind the unchanged `KnowledgePort` (`say`, `record_facts`, `planning_digest`). The graph (`graph.py`) was not touched.

- **D51 - Cards/strings/snapshots schema.** Three tables, migration `0004_cards_strings_snapshots` (revises `0003_project_phase`): `cards` (id, project_id, kind, coverage_area, body, status, version, created_at — `kind` allows all 15 D22 kinds even though v1 only writes a subset, `app/agents/card_kinds.py` is the source of truth), `strings` (id, project_id, kind, from_card_id, to_card_id, created_at — only `supported-by` is written in v1; `derived-from`/`depends-on`/`conflicts-with` are reserved, never an untyped `related-to`), `snapshots` (id, project_id, phase, card_versions, accepted_by_account_id, created_at). No DB-level `CHECK` constraints, matching the rest of this schema (`Job.status`, `GateActionIn.action`) — kinds/statuses are validated in Python. **Snapshot shape: pointers to card versions**, not a JSON blob of prose and not a stored document — `card_versions` is a JSONB array of `{card_id, version}` pairs (the rethink's stated preference, D17). All three tables use the same `JSON().with_variant(JSONB, "postgresql")` pattern as `messages.widget`, so they work unchanged on SQLite (tests) and Postgres.
- **D52 - Area→kind mapping and gate-time promotion.** `app/agents/card_kinds.py` maps every Planning and Requirements coverage-area key (`templates.py`) to a D22 card kind, as data, not branching code; unmapped areas and `general` (post-revise listening, `current_area is None` in `graph.py`'s `wait` node) fall back to `open_question`. At gate accept, `runner.py`'s `on_accept()` calls `services/cards.py:freeze_snapshot`, which promotes every non-`accepted` card whose `coverage_area` is one of that phase template's own area keys to `accepted`, then freezes a snapshot over those cards plus their linked `source` cards — chosen over the alternative (leave everything `candidate`, snapshot only) because D17/D20 tie acceptance to a name-and-timestamp event, and an `accepted` status is how that shows up on the card itself, not just in the snapshot row. Documented gaps, deliberately not solved here: `general`-area cards are excluded from automatic promotion (area keys carry no phase marker, and while Planning's and Requirements' area-key sets don't overlap so scoping by template area is exact for named areas, a `general` card can't be attributed to a phase this way) — they stay `candidate` until a later pass; `confirmed` status is unused in v1 (duplicate/conflict corroboration is the belief layer's job, out of scope here).

## Snapshots, views, and session token (2026-08-18)

- **D53 - Session JWT.** The `crewlane_session` cookie is a HS256 JWT (`sub` = account_id, `exp` = 14 days), signed with `DEV_SESSION_SECRET`. Still HttpOnly + SameSite=lax; still not Stytch; frontend never stores the token. Replaces the custom HMAC blob from D42. Logout still deletes the cookie.
- **D54 - Snapshot views.** `GET /projects/{id}/snapshots` returns each frozen snapshot with a **deterministic** Charter/SRS body rendered from card pointers (no LLM). Workspace lists cards (`GET /projects/{id}/cards`) and shows Charter/SRS from the latest snapshot per phase.

## Ingestion lane (2026-08-18)

Recorded with `feat/8-ingestion`; implements the capture → normalize → extract half of D13. Belief layer and pgvector retrieval are the next lane on the same pipeline.

- **D55 - Ingestion pipeline v1.** `POST/GET /projects/{id}/uploads` accepts multipart files (max 25 MB). Supported formats: txt, md, pdf (PyMuPDF), docx (python-docx), and audio (wav/mp3/m4a/webm/ogg/flac → Groq Whisper when `GROQ_API_KEY` is set; scripted placeholder otherwise). Raw bytes land in object storage via `app/adapters/storage.py`: **MinIO in docker-compose** (S3 API, D34) when `S3_*` env vars are set; **local disk** (`LOCAL_UPLOAD_DIR`) when they are not — same port shape, no vendor lock-in (D41). Upload row carries dual provenance fields (`submitted_by_account_id`, optional `speaker_name`); source cards use `upload:{id}` refs. A Postgres `jobs` row (`kind=ingest_upload`) is processed by the in-process worker (D32, enabled in compose via `JOB_WORKER_ENABLED=true`). Worker path: fetch → parse or transcribe → chunk (`evidence_chunks` table, migration `0005_uploads_evidence`) → LLM extract facts → `record_facts` in `general` area. Chat extraction (D47) is unchanged. **Still deferred:** xlsx/images (D39), ffmpeg long-audio chunking, per-chunk `supported-by` strings, area inference from upload content.

## Belief and retrieval lane (2026-08-18)

Recorded with `feat/9-belief-rag`; completes the D13 belief-layer tail and wires retrieval into the graph digest.

- **D56 - Belief layer + retrieval v1.** All facts (chat extraction and ingestion) pass through `app/services/belief.py` before landing as cards. **Duplicate** (cosine ≥ 0.92 with Gemini embeddings, or high text similarity without a key): existing card → `confirmed`, extra `supported-by` to the new source. **Conflict** (similarity ≥ 0.78 + LLM `conflict_check` when Groq is available): new candidate card + `conflicts-with` string to the matched card; `GET /projects/{id}/conflicts` exposes pairs for the review UI (widget deferred). Embeddings: Gemini `text-embedding-004` via `GEMINI_API_KEY` (`app/adapters/embeddings.py`); stored as JSON on `cards.embedding` and `evidence_chunks.embedding` (migration `0006_embeddings`; `CREATE EXTENSION vector` on Postgres for forward compatibility). Ingestion embeds chunks when the key is set. `app/services/retrieval.py` ranks cards + evidence by similarity; `CardKnowledge.planning_digest()` and the graph `ask` node consume retrieved context so the interviewer does not re-ask what uploads already answered. **Deferred:** HNSW index, chunk-level provenance strings.

(b) Substantive floor: 3+ extracted facts for the asked area covers it even if the model hesitates. (c) Coverage meter re-emits on every area completion/N-A. ## RAG pipeline rework (2026-08-19)

Recorded with `feat/rag-pgvector-rework`; closes D56's deferred "HNSW index" line item and D39's parsing gaps. Images explicitly out of scope (existing Groq-vision path untouched). Hybrid (vector + keyword) search was deferred out of the initial pass as its own future lane - then added on this same branch once the pgvector groundwork was proven (D66 below), rather than opened as a separate effort.

- **D63 - Real pgvector, not just the extension.** `cards.embedding`/`evidence_chunks.embedding` are now `pgvector.sqlalchemy.Vector(768)` columns (migration `0009_pgvector_embeddings`) with an HNSW index (`vector_cosine_ops`, pgvector's own `m=16, ef_construction=64` defaults) on each — not the plain JSON columns D56 shipped "for forward compatibility." **Dimension: 768** (one of `gemini-embedding-001`'s Matryoshka-truncatable official sizes; the full ~3072 default was unrequested precision for short fact/requirement-sentence retrieval at this system's per-project scale), requested explicitly via `outputDimensionality` in every embed call (`app/adapters/embeddings.py`) — previously never set at all. **Index choice, HNSW over IVFFlat:** IVFFlat needs a `lists` parameter tuned to expected row count and degrades as data outgrows that tuning, with no rebuild job anywhere in this codebase; HNSW builds incrementally with no size-tuning parameter, matching how this system's cards/chunks actually grow (one interview turn or upload at a time, never bulk-loaded). **`retrieval.py`/`belief.py` rewrite:** `retrieval_context()` and `_best_match()` now run indexed `ORDER BY embedding <=> :query LIMIT k` / `WHERE distance <= threshold` queries on Postgres when a query embedding exists, falling back to the pre-existing Python `_cosine`/`_text_similarity` linear scan on sqlite (tests), when no embedding exists (no `GEMINI_API_KEY` — embeddings stay non-load-bearing, D56's soft-fail philosophy unchanged), or on any `SQLAlchemyError` (with `session.rollback()` before falling through, since Postgres aborts the transaction after a statement error). **Scale note, addressed explicitly rather than assumed:** every query was already `WHERE project_id = :id` first, so the real gap this closes is protection against one project's own dataset growing large, not cross-project scan cost — that was already bounded by project scoping. New operational safeguard: a startup warning (`app/main.py`) fires when Postgres is configured but `GEMINI_API_KEY` is unset (text refined in D67 once D66 added keyword-only FTS). `scan_conflicts()` (belief.py's meaning-first LLM conflict check, D62-era) is untouched — similarity-unrelated by design, out of scope. **New test pattern:** `tests/test_retrieval_pgvector.py` is this repo's first Postgres-only test, gated on `PGVECTOR_TEST_DATABASE_URL` (not `DATABASE_URL`, which `conftest.py` unconditionally forces to sqlite before pytest collects) — skipped by default, run locally against `docker compose up -d postgres`. Every other test stays sqlite-only, exercising the preserved fallback path with hand-set embedding vectors instead.
- **D64 - Chunking overlap + sentence-aware fallback; DOCX tables.** `chunk_text()` (`app/services/parsers.py`) gained a 150-char default overlap between consecutive chunks (previously zero — a fact split across a chunk boundary had no redundancy carrying it into both sides) and a sentence-boundary-aware fallback tier for a single oversized paragraph, ahead of the previous raw fixed-window cut (now the last resort, only when a "sentence" has no `.`/`!`/`?` at all). Stays character-based, not token-based, deliberately: no tokenizer (`tiktoken` or otherwise) exists anywhere in this repo's dependency tree, and adding one solely for chunking wasn't judged worth it for a heuristic that's already adequate at this content length. `.docx` extraction now also reads `doc.tables` (pipe-joined cells — DOCX table prose routinely contains commas, unlike CSV/XLSX), previously silently dropped.
- **D65 - RAG polish on top of D63.** (a) **Unified cross-corpus ranking**: `retrieval_context()`'s pgvector path used to fetch `limit` cards and `limit` chunks independently, so a project with strong evidence but weak cards (or vice versa) could have real hits crowded out before the two lists ever competed. Now each corpus is overfetched at `limit * 2` and merged by score before trimming to `limit` (`_merge_top()`). (b) **Evidence provenance**: hits were labeled bare `[evidence]`, useless once a user asks "what does the SOW say" about a specific file. Now `[evidence:{filename}#{chunk_index}]` (`_evidence_label()`), on both the SQL path (`Upload` join) and the Python fallback (uploads pre-loaded into a dict keyed by id). (c) **Re-embed on edit**: `PATCH /cards/{id}` (D62-e) set `embedding = None` expecting a "lazy" re-embed that nothing ever triggered, so an edited card silently dropped out of vector retrieval/dedupe permanently. New shared `belief.embed_fact(text)` (soft-fails to `None` without `GEMINI_API_KEY`, same as everywhere else) is now called immediately in `cards.update_card()` and for the new card `add_conflicting_fact()` creates on a conflict resolution (previously left `embedding=None` there too, same silent-drop bug one step earlier). Belief dedupe (`_best_match()`) itself is untouched — stays vector-or-text, no keyword logic, per D63.
- **D66 - Hybrid retrieval: vector + full-text search, `retrieval_context()` only.** Real product need surfaced during demo prep: exact-token recall for proper nouns ("Stripe", "Mindbody"), numbers ("70%"), and codes/acronyms — cosine similarity over embeddings blurs exactly these, since a short exact term can sit far from a paraphrase-shaped query in embedding space even when it's the literal right answer. Migration `0010_hybrid_fts` adds a Postgres `GENERATED ALWAYS AS (to_tsvector(...)) STORED` `search_vector` column + GIN index on `cards.body` and `evidence_chunks.body` (Postgres-only, no-op on sqlite — same shape as `0009`). **`'simple'` config, not `'english'`**: English stemming/stopword removal actively works against exact product names and short codes, which is the entire point of this lane; `'simple'` does no stemming and drops no stopwords. **Not ORM-mapped**: `search_vector` is referenced via bare `sqlalchemy.column("search_vector", type_=TSVECTOR)` constants in `retrieval.py`, not a `Card`/`EvidenceChunk` attribute — it's a Postgres-only generated column with no sqlite equivalent and nothing should ever assign to it from Python, so keeping it out of the cross-dialect model avoids both problems at once. **Fusion**: `_rrf_fuse()` (reciprocal rank fusion, k=60) combines the vector-channel and keyword-channel rankings by rank position, not raw score — cosine similarity and `ts_rank` live on unrelated scales, so fusing the numbers directly would let whichever produces bigger values dominate regardless of actual relevance. **Flow in `retrieval_context()`**: on Postgres, keyword search always runs when the query is non-empty (works with or without an embedding); the vector channel runs whenever a query embedding exists; one channel found → used as-is, two channels → RRF-fused. This also means a `GEMINI_API_KEY`-less Postgres deployment now degrades to **keyword-only FTS** instead of falling all the way to the O(n) Python scan (D67 refines the startup warning text to say this explicitly). **Scope, deliberately narrow**: `retrieval_context()` only — belief dedupe (`_best_match()`) and `scan_conflicts()` are untouched; hybrid search answering "what does the evidence say" is a different problem from "is this the same fact as one we already have," and D63 already reasoned through why dedupe stays vector-only. **New test**: `tests/test_retrieval_pgvector.py` gained `test_hybrid_search_finds_exact_term_vector_alone_would_miss` (a chunk whose embedding is deliberately pointed away from the query vector, findable only via its exact keyword) and `test_keyword_only_search_works_without_an_embedding` (no `GEMINI_API_KEY`, proving the keyword-only branch runs without ever touching the vector channel).

## RAG hardening after the Stage 1/2 evaluation (2026-08-25)

Recorded on `feat/embeddinggemma-docling-only`, driven directly by findings from the RAG evaluation harness (`backend/evals/`, `CrewLane-RAG-Evaluation-Stage-1-and-2.docx`) built to answer whether D73/D74's semantic foundation and the structured retrieval/grounding layer on top of it are production-ready. Two real correctness gaps were found by reading the production code the eval was scoring and by directly probing Postgres, not by the eval's own summary metrics alone - the eval's `production_hybrid` row looked fine in isolation because its ranking metrics were already strong; only per-query inspection of deliberately unanswerable questions (R-038, R-040 in `retrieval_baseline_report.md`) exposed that it never actually declined to answer.

- **D75 - Hybrid retrieval could never abstain; the FTS channel was the reason, and it's now judged instead of trusted blind.** Root cause, confirmed empirically against live Postgres before touching any code: `_lexical_query()`'s OR-joined `to_tsquery('simple', ...)` treated every query word as a first-class match term, including pure function words ("what", "did", "we", "about", "that"). `'simple'` (D66) has no stopword list by design, so any real paragraph containing even two or three of these extremely common words could clear `rag_fts_min_rank` on stopword overlap alone, regardless of topical relevance - confirmed directly: `to_tsquery('simple', 'what | did | we | decide | about | that')` matched an unrelated sentence purely because it contained the word "that" (`ts_rank_cd` = 0.1 from that single hit). Effect on `production_hybrid`: **no-answer correctness was 0.000** - it returned five results for every query in the eval corpus, including the two deliberately unanswerable ones, when every stricter method (any vector floor, FTS alone, RRF-fused hybrid with a floor) correctly returned nothing for those two. That pushed the entire "is there actually an answer here" decision onto the downstream grounding judge - which had its own gap, below. **Fix**: `_lexical_query()` now filters stopwords server-side before the OR join - `SELECT lexeme FROM unnest(tsvector_to_array(to_tsvector('simple', :query))) WHERE to_tsvector('english', lexeme) <> ''`. This keeps `'simple'`'s no-stemming matching against the (`'simple'`-indexed) `search_vector` columns - D66's proper-noun/identifier reasoning is untouched, verified directly: `Stripe`, `70`, and `REQ-ACC-003` all survive the filter intact - while dropping function words using Postgres's own built-in English stopword table, not a list this codebase authors or maintains. Zero added round trips: the filter runs inside the same statement Postgres was already executing. **Re-running the full retrieval baseline after the fix, same corpus, same queries**: `production_hybrid` no-answer correctness **0.000 -> 0.750** (now matches `vector_0.35`'s own abstention rate), while every ranking metric *also* improved (R@1 0.861->0.889, MRR 0.931->0.944, nDCG@5 0.903->0.923, P@5 0.367->0.378) - fixing the bug removed literal noise from the fusion, so it helped ranking quality and correctness at the same time rather than trading one for the other. R-038 and R-040 (the two unanswerable queries) both went from returning low-score noise to `no results`.
- **D76 - Grounding judge now runs whenever evidence was retrieved, not only when the model cited it correctly.** `rag.py`'s `enforce_grounding()` used to skip the LLM grounding-judge check entirely whenever `validate_citations()` found the reply ungrounded - which includes the reply citing nothing at all, or citing a mix of valid and fabricated markers. A model that skips its citation instructions is exactly the case most likely to be hiding an unverified or hallucinated claim, and it was the one case that bypassed the safety check completely rather than the one case that most needed it. Combined with D75 (retrieval that always returns *something*), this was a real path from "no real evidence for this" to "unverified answer reaches the user" with nothing in between. Fix: the judge now runs whenever `result.hits` is non-empty, judging the model's original reply text (not the citation-footer-appended copy `validate_citations` may have produced, which isn't part of what the model actually claimed); an uncited or invalidly-cited reply that the judge can't support now correctly returns the existing "I couldn't verify that answer" abstention instead of passing through unverified. New tests: `test_grounding_guard_judges_uncited_scripted_answer`, `test_grounding_guard_returns_unchanged_with_no_hits` (`tests/test_rag.py`).
- **D77 - Exact-match channel gets a real index; chunk/retrieval knobs stay out of source.** (a) `_exact_channel()`'s `lower(body) LIKE '%term%'` (up to 12 terms, two tables) was a sequential scan with no index support - fine at eval-corpus scale (26 rows), not fine as a project's evidence grows. Migration `0013_exact_channel_trgm_index` adds `pg_trgm` + a `gin (lower(body) gin_trgm_ops)` index on `cards`/`evidence_chunks` (Postgres-only, no-op on sqlite, same shape as `0009`/`0010`). Measured effect on `production_hybrid` mean latency: 445.8ms -> 360.9ms: real, but the channel is still the slowest part of the fused query relative to vector's ~97ms - worth watching as corpora grow past this eval's size, not yet worth restructuring further. (b) `docling_parser.py`'s `HybridChunker` token cap was a bare module constant (`_MAX_CHUNK_TOKENS = 256`); moved to `Settings.docling_max_chunk_tokens` (default unchanged) so it sits alongside the `rag_*` knobs already environment-configurable for the same reason - not tied to a particular document type or fixture. Behavior-neutral: chunking eval reproduced the identical 16-chunk/29-fact result before and after.
- **D78 - Frontend: a transient fetch failure is not "the project doesn't exist."** `ProjectWorkspace`'s initial-load effect (`frontend/app/projects/[id]/page.tsx`) caught any failure from its bootstrap `Promise.all` - a real 404, a CORS error, the backend mid-restart, anything - and rendered the same "Project not found" full-page state for all of them, because `lib/api.ts`'s `request()`/`requestForm()` threw a plain `Error` that discarded the actual HTTP status into an unstructured string. New `ApiError` (extends `Error`, carries `status`) lets the catch handler tell them apart: only a genuine `404` sets the "not found" state now; anything else shows a retryable error banner (`Retry` re-invokes the same load) instead of falsely claiming the project is gone. Found live: a docker rebuild's restart window produced exactly this false "Project not found" on a project that was serving 200s minutes later.

Eval reports and the evaluation document (`CrewLane-RAG-Evaluation-Stage-1-and-2.docx`) were regenerated against these fixes - see that document for the full before/after tables and the revised production-readiness conclusion.

- **D79 - LangGraph checkpointer used a single unpooled connection with no health-checking; found live via a 100%-reproducible chat-history failure.** `runner.py`'s `init_checkpointer()` created one raw `psycopg.Connection` at app startup and cached it forever in a module-level global - unlike the regular ORM session (`db.py`'s `pool_pre_ping=True`), this connection was never health-checked or replaced. Once it died (a transient network drop is enough - the same class of Docker/WSL2 networking issue this session hit twice elsewhere), every subsequent `GET /projects/{id}/messages` failed identically (`psycopg.OperationalError: the connection is closed`, traced through `ensure_phase_started` -> `graph.get_state()` -> `PostgresSaver.get_tuple()`) until the next container restart - confirmed live, 9/9 failures over 30 minutes, 100% reproducible, not intermittent. Every other project endpoint (cards, uploads, audit, snapshots, conflicts) was unaffected, since none of them touch the checkpointer. Fix: `PostgresSaver` is now constructed from a `psycopg_pool.ConnectionPool` (verified against the installed library source: `PostgresSaver.__init__` and its internal `_cursor()`/`get_connection()` both natively branch on `ConnectionPool` vs. a bare `Connection`) instead of a single connection - `min_size=1, max_size=5`, sized small deliberately per D63's reasoning (this app grows one interview turn at a time, not high concurrency). A pool checks connection health on checkout and transparently swaps in a live one, the same protection `pool_pre_ping` already gives the ORM-backed session. `psycopg-pool` is not a new dependency - it is already pulled in by `langgraph-checkpoint-postgres`, which the checkpointer already required.
- **D80 - `complete_json()`'s repair-retry never ran when Groq's own JSON-mode validation rejected a completion; found live via a real, reproducible "Generate selected" failure on the stories pack.** `_stories_json()` (`documents.py`) calls `complete_json(..., attempts=3, json_mode=True)` to build the Epics -> Features -> Stories deliverable's large nested JSON tree. `complete_json()`'s retry loop (`inference.py`) only handled the case where the model returns text `parse_json_object()` fails to parse - it had no `try`/`except` around the `inference.complete()` call itself. When Groq's `response_format={"type":"json_object"}` server-side validation rejects a malformed completion outright, the SDK raises `groq.BadRequestError` (code `json_validate_failed`) instead of returning text - a different failure shape entirely, and one that skipped both this retry loop and `_stories_section()`'s own fallback (which only catches its typed `_StoriesGenerationError`, not a raw provider error). The exception propagated all the way through `graph.py`'s `gate_wait` unhandled, surfacing as a bare 500 on `POST /projects/{id}/gate` - confirmed live, twice, both times while generating multiple detailed user stories in one call (the largest, most fragile schema this app asks an LLM to produce in a single shot). Fix: `complete_json()` now catches `groq.BadRequestError` specifically, logs it, and continues to the next retry attempt - reusing the model's own rejected `failed_generation` text (Groq returns it in the error body) as the repair turn's starting point instead of blank context, so the retry has something concrete to correct rather than starting over blind. New test: `test_complete_json_retries_past_provider_json_validation_rejection` (`tests/test_deliverables.py`), constructing a real `groq.BadRequestError` to prove the retry path, not just the parse-failure path the existing test already covered.

## Bounded tool-calling retrieval (2026-08-26)

- **D81 - The turn node decides-and-answers via one bounded tool call instead of a separate `decide_retrieval()` routing call plus a generate call.** Recorded on `feat/rag-bounded-tool-retrieval`, off `main` (D73-D80 already merged there via PR #41). Previously every turn cost two full LLM calls regardless of outcome: `decide_retrieval()` (routing) always ran first, then a separate `complete_json()` generated the reply - even when the router decided nothing needed retrieving. New `GroqInference.complete_with_tools()`/`ScriptedInference.complete_with_tools()` (`inference.py`) offer the model exactly one function tool, `search_project_evidence` (`rag.py`'s `SEARCH_EVIDENCE_TOOL`), with `tool_choice="auto"` - the model either answers directly in that same call (JSON content, parsed via `parse_json_object()`), or requests the tool once. **Net call count, precisely**: when no retrieval is needed, this is **one call, down from two** - a real reduction. When the model does reach for evidence, `knowledge.retrieve()` runs (no LLM cost), and a follow-up `complete_json()` call produces the final answer using the retrieved evidence - **two calls, the same as before**, never more: the follow-up call is offered **no tools at all**, so "at most one retrieval, once" is enforced structurally (the model cannot loop or chain calls), not by trusting the model to stop on its own. `enforce_grounding()` (D76) is unchanged - it still runs as its own separate, forced call whenever `result.hits` is non-empty, independent of how retrieval was triggered; folding grounding verification into the same call that decided to trust the evidence would undo the reasoning D76 was built on (a model should not be the sole judge of whether its own uncited claim is safe). `decide_retrieval()`/`RetrievalDecision` are left in place, unused by the turn node but still tested (`test_rag.py`), so the previous approach stays available for direct comparison rather than deleted outright. **Known, deliberate limitation, not hidden**: the direct-answer branch has no repair-turn retry if the model's JSON content is malformed (unlike `complete_json()`'s multi-attempt loop) - adding one would reintroduce a form of looping this design explicitly avoids; a parse failure here soft-fails to `{}` the same way `complete_json()` does when its own attempts are exhausted. New tests: `test_search_evidence_tool_is_a_single_bounded_function_tool`, `test_scripted_complete_with_tools_calls_tool_for_a_question`, `test_scripted_complete_with_tools_answers_directly_for_a_statement`, `test_groq_complete_with_tools_parses_tool_call_and_survives_bad_arguments` (`tests/test_rag.py`); `test_bounded_tool_retrieval_fires_for_a_question_never_for_a_statement` (`tests/test_agents.py`), confirming both branches end to end via the real HTTP flow, not just in isolation. **Explicitly out of scope**: SerpAPI/web search was not touched - it stays exactly as it was (feasibility-gate-triggered only), per an explicit decision not to give the agent open-ended access to a paid, externally-metered API on top of this change.

## Junk-upload / relevance filtering at ingestion (2026-09-16)

- **D86 - Off-topic content is classified before it is persisted, not stored then filtered; whole-document rejection is human-confirmed, not silent.** Uploads with no bearing on a project (the wrong file, unrelated background material) were previously ingested unconditionally — `process_ingest_job` (`ingestion.py`) had no relevance check at all, only Docling's not-empty guard. Fix folds a relevance judgment into the per-chunk extraction call that already runs (`_extract_system()` gains an `on_topic` field once a scope exists to judge against — zero added LLM calls), and **reorders persistence to happen after classification**: an off-topic chunk gets no `EvidenceChunk` row, no embedding, and no `Card` at all, rather than being stored and excluded from card-creation after the fact — the deliberate choice was that junk must never be able to leak back out through retrieval or chat asides, which storing-then-filtering would not prevent. **Mixed-relevance documents** (partly on-topic, partly not) are handled automatically at this chunk granularity with no human interruption — a document that is mostly relevant with some noise simply keeps only the on-topic chunks' facts. **Whole-document rejection is different**: when *every* chunk in an upload is judged off-topic (`_extract_chunks`'s `kept_chunks == 0`), that usually means the wrong file was dropped in entirely, not ordinary noise — the upload is marked `status="flagged"` and a chat widget (`off_topic_upload`) offers **Keep anyway / Discard**, matching this app's existing human-decides-at-every-gate pattern (conflict review, acceptance panel) instead of silently discarding a file an LLM misjudged. `POST /projects/{id}/uploads/{upload_id}/keep|discard` resolve it; `has_pending_intake()` also blocks the interview on any `flagged` upload, so intake fully resolves (read or explicitly excluded) before questions start, consistent with the existing "read everything before asking" ordering. **Early-project bypass, not a tuning parameter**: `_project_scope_digest()` returns `""` (gate off, every chunk on-topic — identical to pre-D86 behavior) while the project has neither a brief of any real length (<40 chars) nor a handful of recorded facts yet (<3), because the *first* uploads to a brand-new project often are what defines its scope (the existing "read everything before asking a single question" front door) — judging them against a scope that doesn't exist yet would reject the very documents that should be shaping it. The fact threshold is a small handful, not zero, because `mine_brief()` already records at least one fact from the brief itself at project creation — gating on "zero facts" would flip the check on before any real evidence had a chance to shape the project (caught by re-running the test suite: `test_process_ingest_extracts_facts` and `test_ingest_conflict_records_open_conflict` both regressed under a zero-facts threshold, since a single incidental brief-mined fact was enough to activate the gate one upload later). The reference used once active is `project.brief` + accumulated coverage-area facts (`cards_service.digest_lines`), not the brief alone, so the check gets more accurate as the project fills in. **Considered and rejected**: embedding-cosine or cross-encoder-reranker scoring alone (`adapters/embeddings.py`/`adapters/reranker.py` both already exist and are reusable) — cheaper, but too blunt as a sole decision-maker against a short/vague brief, with damaging failure in both directions; per-fact (rather than per-chunk) relevance judgment — more granular but redundant, since the same extraction call already reads and classifies each fact and chunks are already paragraph/section-sized. New tests in `tests/test_ingestion.py` (`test_early_project_bypasses_relevance_gate`, `test_off_topic_upload_flagged_and_not_persisted`, `test_keep_flagged_upload_ingests_previously_skipped_content`, `test_discard_flagged_upload_stays_empty`); `ScriptedInference`'s `ingest_extract` branch (`inference.py`) gained a deterministic word-overlap heuristic for `on_topic`, mirroring `conflict_scan`'s existing scripted-test pattern.
- **D87 - D86's on-topic judgment tightened to an explicit same-subject comparison; found live against the real model, not the scripted stand-in.** Manual testing with real Groq (not `ScriptedInference`) surfaced a gap D86's tests didn't cover: a project briefed as `"todo app to keep track of daily activities"` had a complete, coherent, well-written brief/kickoff-notes/stakeholder-register set for an entirely different, named product (`"CampusLab Equipment Booking Portal"` — lab equipment bookings, approval workflows, lab managers) judged `on_topic: true` for every chunk, and its facts were recorded as if relevant. Root cause: `_extract_system()`'s on-topic instruction asked a vague "does this seem unrelated" question and defaulted to `true` whenever unsure or when content was "neutral/general" — a full, polished, internally-coherent document for a different product doesn't read as "unsure" or "neutral" to a model, so the leniency built to protect real-but-oddly-phrased evidence (D86's stated concern) was also protecting a completely different project's documents from correct rejection. **Fix**: the instruction now forces an explicit same-subject comparison — what specific product/system does the scope describe, and does the evidence describe that same one — and states plainly that a well-written, internally-coherent document is not on-topic merely because it resembles real project material (stakeholders/scope/risks sections mean nothing if the product they describe differs). The leniency default is narrowed to apply only to content with no specific subject of its own (a generic risk statement, a stray scheduling note), not to content that clearly belongs to its own, differently-scoped product. No schema change (`on_topic`/`facts` shape untouched) and no added LLM call — wording-only change to the same single per-chunk call. **Verified against the live model, not just the scripted stand-in** (the scripted heuristic's word-overlap check wasn't what was wrong — the real model's reasoning was): re-ran the exact failing scenario end-to-end via the running Docker stack — the CampusLab documents against the todo-app brief now return `status="flagged"`; a genuinely relevant todo-app upload to the same project still completes normally; a mixed document (one relevant paragraph, one paragraph about unrelated lab-equipment-calibration content) still completes with only the relevant paragraph's facts recorded, confirming the tightened wording didn't overcorrect into rejecting real content. Full backend suite (160 tests) and ruff stayed green throughout — the scripted-test suite doesn't exercise this specific reasoning gap (it only needs word-overlap to differ, which was never the broken part), so the live-model re-test is the operative verification for this fix, not the unit suite alone.
- **D88 - Frontend upload-poll completion check never recognized "flagged" as finished, so a flagged upload's chat message never got fetched.** Found live: uploading files that all got flagged (D86/D87) left the chat pane permanently empty — the Evidence panel correctly showed "Needs review," but no `off_topic_upload` message with Keep anyway/Discard ever appeared, with no error anywhere. Confirmed via the API directly (`GET /projects/{id}/messages?phase=planning`, authenticated as the actual project owner) that the messages existed in the database with correct content, widget data, and `phase` all along — this was a pure frontend gap, not a backend one. Root cause: `page.tsx`'s 3-second upload-status poll (added before D86 existed) only called `refreshWorkspace()` — the only thing that fetches new chat messages — once `uploadRows.every(u => u.status === "done" || u.status === "failed")`. `"flagged"` was never in that list, so once any upload reached it, the completion condition could never become true again; the poll ran forever checking upload status (keeping Evidence/Artifacts accurate) but never re-fetched messages. Fix: redefined "pending" for this poll to mean actual background work (`"queued"`/`"processing"`) rather than "not done/failed" — `"flagged"` is finished from the *job's* perspective (nothing left running), only a human decision is outstanding, and that decision's own handlers (`keepFlaggedUpload`/`discardFlaggedUpload`) already call `refreshWorkspace()` themselves. So the poll now stops and does its one final `refreshWorkspace()` the moment nothing is queued/processing, whether that end state is done, failed, or flagged. Frontend lint/build/typecheck stayed clean; manually re-verified against the live app that a freshly-flagged upload's chat card now appears within one poll tick (≤3s) instead of never.

## Bidirectional Planning/Requirements editing (2026-09-21)

- **D89 - Planning becomes reopenable after acceptance via a targeted single-area redraft; Requirements detects and redirects Planning-shaped statements instead of recording them; Requirements deliverables carry a coarse staleness signal against later Planning changes.** Planning was accept-once, permanently read-only (`assert_tab_writable`'s hard-coded "Planning chat is read-only after the Charter is accepted") — real projects change charter-level facts after Requirements has already started, with no way to fix that without it being misfiled as a Requirements answer, and no signal that an already-generated Requirements deliverable predates a later Planning change. **Correcting the original framing before building anything**: the `cards` table (long-term memory) is already shared and live across phases — `render_snapshot()` (`cards.py`) resolves its pointers against the *live* `Card` row, not a pinned version, so a Planning edit is visible to any re-render immediately with no sync needed. What actually needed a staleness signal is only *already-generated static text* (a frozen `Snapshot.narrative`, an exported OneDrive file), not the underlying facts. **Two corequisite bugs found and fixed along the way, not worked around**: (1) `runner.py::_graph()`'s Planning thread id was an inlined literal (`f"{project.id}:planning"`), a *second*, independent source of truth from `chat_threads.planning_thread_key()` — versioning one without the other would have desynced the message thread from the LangGraph checkpoint thread the moment a redraft used a new version; both now go through one versioned `planning_thread_key(project_id, version)`, which keeps returning the legacy unversioned key at version 0 (the original pre-first-accept interview) so already-running/already-accepted projects' checkpoints don't shift under a deploy, and only starts appending `:vN` for N ≥ 1 (a redraft, which by definition only starts after the first accept). (2) `freeze_snapshot()`'s single query (`status.notin_([ACCEPTED, RETIRED])`) was used for *both* deciding which cards to promote *and* building the snapshot's pointer list — correct on a first accept, silently wrong on any second accept that doesn't touch every area (a targeted one-area Planning redraft, by design, never does): untouched areas' cards are already `status="accepted"` from snapshot v1 and would be excluded from v2's pointers entirely, rendering a Charter missing every section except the one just redrafted. No existing test exercised a second `freeze_snapshot()` call, so this had never been caught. Fixed by splitting into two queries: promotion stays scoped to the not-yet-accepted delta; pointers are built from every current, non-retired card in the template's areas regardless of status, so every snapshot (Planning or Requirements, first or Nth accept) is self-contained. **Part 1 (reopen + redraft)**: `_graph()` gains a `phase_override` param so it can build the Planning graph while `project.phase` stays on `"requirements"`/`"done"` — a new `Project.planning_redraft_active` bool (not `phase`) is what makes the Planning tab writable again during that window; `on_accept`'s phase-advance line is conditional on this so a redraft's re-accept can never silently un-complete a `DONE` project. New `start_planning_redraft(area=None)` mirrors `start_requirements_redraft`'s fresh-thread jump straight to `pick → gate_emit`, then — since the ask was "change this one thing," not "redo all of Planning" — optionally chains one more resume into the existing `action == "revise"` gate branch (`_start_gate_revise`, unchanged) for a single targeted question, rather than re-running the full interview and re-synthesizing proposals for untouched areas. Auto-feasibility re-research is skipped on a redraft for free, by the existing `on_gate_research=... if phase_key == project.phase else None` guard (phase_key `"planning"` ≠ live `project.phase` during a redraft) — not new logic, just documented as deliberate. **Part 2 (cross-phase redirect)**: a new, narrow, *second* classification call inside `wait()`, not folded into the main turn-extraction schema — that schema has zero knowledge of Planning's areas (it's built entirely from whichever template is live), and combining "which Requirements area?" with "is this actually a different phase?" in one judgment is the same overloaded-schema failure shape D87 already had to fix for `on_topic`. Gated on the exact same rare `on_topic=false, has facts` branch the existing within-phase reclassify already pays for (not a new always-on call), and only when `template.key == "requirements"` (Planning has no phase "above" it). A true result never auto-writes a Planning card or silently keeps it as a Requirements fact — it emits a `phase_redirect_suggestion` widget (mirrors `off_topic_upload`'s two-action shape from D86: "Go to Planning" / "No, keep it here") and re-surfaces the still-open Requirements question, leaving the human to decide. **Part 3 (staleness)**: `cards_service.requirements_stale_since()` compares the latest Planning `Snapshot.created_at` against the latest Requirements one (`>=`, not `>` — a tied timestamp under low-resolution storage should read as stale rather than silently hide a possibly-real change; false-stale only costs a dismissible banner, false-not-stale hides an actual change), surfaced via a new `ChatStateOut.requirements_stale_since` field as a banner pointing at the existing "Redraft requirements" button — coarse, document-level, human-reviewed, no auto-regeneration. **Rejected**: full Planning re-interview on every redraft (the user's own framing was "change this one thing"); folding the redirect check into the main extraction schema (the D87-style overloaded-judgment risk above); fine-grained per-fact staleness diffing between Planning snapshots (more precise than asked for, and cards are already live so a diff would mostly restate what re-rendering already shows). New tests in `tests/test_bidirectional.py` cover: a redraft targeting one area's question (not a full re-interview); a second accept's rendered snapshot retaining every area's content (the `freeze_snapshot` regression); a redraft cycle from `DONE_PHASE` leaving `project.phase` unchanged; the message-thread key and the graph-checkpoint thread id agreeing; a Planning-shaped Requirements statement producing the redirect widget with no card recorded either way; and the staleness signal appearing after a Planning redraft postdates the last Requirements accept. Full backend suite (170 tests) and ruff stayed green throughout.
- **D90 - First live test of D89 surfaced a double-fire button, a question-drafting drift, and a real feature gap in post-completion chat; each traced to a distinct, confirmed root cause via the DB audit trail before fixing.** All three found in one live session on a project called "Cloud Pulse," none of them related to the others despite surfacing together. - **D91 - First real end-to-end Playwright run (not curl/API calls) against D89/D90 found two more live bugs in minutes: a staleness false-positive on brand-new projects, and a redirect-detection blind spot for a whole classification path.** (1) **`requirements_stale_since` showed the "Planning was revised" banner on a project that had only ever accepted Planning once and never drafted Requirements at all.** Root cause: the function treated `last_requirements is None` (Requirements literally never generated yet — the totally normal state for every project between its first Planning accept and its first Requirements accept) the same as "Requirements exists but predates Planning," returning `last_planning` (truthy) in both cases.
