CrewLane

An AI system that runs a software project's lifecycle - with a human decision at every gate. These pages are the single readable summary of the ground-up rethink: what the product is now, how it works, how it's built, what we deliberately changed, and exactly what gets built first.

The idea

What CrewLane is

Everyone already uses AI on project work - ad hoc, with no memory, no process, and no way to tell what the model made up. CrewLane gives that behavior structure. It follows a real software development lifecycle (our baseline is the Teaching Agile process model), interviews you like a good business analyst, absorbs whatever material your project already has, and carries everything from first idea to accepted specification with a full audit trail.

The AI does each phase's work. A named human accepts it before the project moves on. Nothing is ever invented, and everything traces back to who said it.

Three promises define the product:

  • Never invents. What you didn't say is marked not stated - never filled in. Claims about the outside world are researched live, with citations.
  • Everything traceable. Every requirement, risk, and story links back to the exact meeting moment, document line, or message it came from.
  • Humans decide. Phases end at hard gates. Acceptance is a deliberate, recorded act - a name, a timestamp, and an immutable snapshot of what was accepted.

The experience

How it works, start to finish

  1. Sign in.

    The app is the whole site - a sign-in wall with the logo and one line. Enter display name and email; first visit creates your account (JIT). v1 uses a signed HttpOnly session cookie (D42) — not a third-party IdP. We store only name and email on the account row.

  2. Describe your project.

    One free-text box: "What are you building?" No forms. The project name is derived from what you write. New idea or already in flight, greenfield or replacing a legacy system - all four combinations are accepted.

  3. Feed it anything.

    Type freely, upload documents (txt, md, docx, pdf, images, spreadsheets), or upload audio - a Teams recording or a voice note. Raw recordings get transcribed automatically. Everything is stored with dual provenance: who submitted it, and separately, whose words it contains.

  4. The AI reads back before it asks.

    Its first move is a mirror: "Here's what I understood, with sources. Here's what's not stated anywhere." You correct it. For an in-flight project this same step becomes a lifecycle assessment - where you actually are, what's covered, what's missing.

  5. Interview by question cards.

    Small batches of cards, each labeled with why it's being asked, each with an explicit "I don't know / not applicable" option. The agent drops into focused conversation when an answer needs depth. It never asks what your uploads already answered.

  6. Knowledge accumulates as cards.

    Everything learned becomes typed, source-linked knowledge (see the Knowledge Model page). New input is checked against what's known - duplicates strengthen existing facts, contradictions go to a review queue with names attached. Nothing is silently overwritten.

  7. Documents render themselves.

    The Project Charter and the SRS aren't files anyone maintains - they're views generated from the model, always current. Optional: ask for a grounded feasibility study (web-researched, cited, recommendations only).

  8. Hard gates.

    Planning ends when a specific snapshot of the Charter is accepted - deliberately, by name. Requirements inherits everything the Charter established, interviews across nine areas, and ends the same way with the SRS. Chat stays present throughout; there is no wizard.

The knowledge model

Cards and strings

A project's knowledge is stored as typed cards connected by four kinds of strings - not paragraphs in documents. This is what makes documents self-rendering, traceability automatic, and contradictions detectable.

15 card types

source / evidencebusiness needactoruse caserequirementconstraintassumptiondata entityinterfacestoryriskstakeholderdecisionopen questionglossary term

4 string types

  • supported-by - where a fact came from (the provenance spine)
  • derived-from - why it exists (the traceability matrix)
  • depends-on - what must come first
  • conflicts-with - held until a human resolves it

One chain answers the question every real project loses track of:

Jira story ← derived-from ← use case ← derived-from ← business need ← supported-by ← kickoff call, Aug 1, 14:32

Every card carries status (candidate → confirmed → accepted), version history, and priority as fields. Fields for structure, strings for the web - and no untyped "related-to" links, ever.

The belief layer

How new input meets what's known

Every piece of input - a chat message, a document line, a transcript segment - first produces candidate facts, not truth. Each candidate is compared against the existing cards (semantic retrieval over the project's model):

  • New? A candidate card is created, strung to its evidence.
  • Duplicate? It merges into the existing card as corroboration - one more supported-by string, a stronger fact.
  • Contradiction? A conflicts-with string is created and the pair goes to the human review queue, with the names and sources of both sides attached. Nothing is silently overwritten.

Dual provenance is kept throughout: who submitted the material, and separately, whose words it contains. An uploaded recording of someone else's statement credits the speaker, not the uploader.

Process fidelity

The lifecycle, and what we changed

CrewLane follows the Teaching Agile SDLC as its baseline. Every deviation is deliberate, recorded, and reversible - the process itself is versioned configuration (a template: phases, coverage areas, gate rules, document formats), so other organizations' processes become data, not forks.

v1 builds phases 1-2 end to end. The engine is phase-agnostic; later phases arrive as template data plus new capabilities, not rewrites.

Planning, v1 template

  • 4 core areas: business need & vision · scope & exclusions · stakeholders · risks. Follow-ups until substantive, or an explicit N/A with a reason.
  • Feasibility: optional - offered as grounded, cited research with recommendations; never gating.
  • Gate: hard. The Charter snapshot must be accepted, by name, before Requirements begins.

Requirements, v1 template

  • 9 areas: product boundary (inherited from the Charter, not re-asked) · users & goals · tasks & scenarios · failure paths · rules & calculations · data · external interfaces · quality targets with numbers · constraints & compliance (light).
  • Outputs: the SRS view, plus use cases, stories with acceptance criteria, and an always-current traceability view - all rendered from the same cards.
  • Gate: hard, on the SRS snapshot. Jira push is deferred until after the Design phase is designed.
Three recorded deviations from the baseline: (1) resources / timeline / budget dropped from v1 Planning; (2) feasibility made fully optional - the baseline treats its go / no-go as Planning's center, this is our deepest cut; (3) no role separation - anyone in a project can accept, accountability carried entirely by the audit record. Each has a written reason and a template-level return path.

Leverage

Where the AI earns its keep

Measured against the baseline's fifteen requirements-gathering techniques, CrewLane fully mimics nine and partially covers five - and on four of them it beats common manual practice:

  • Interviews - adaptive, always available, never forgets a follow-up.
  • Document analysis - reads everything, links every extracted fact to its line.
  • Benchmarking & research - live web search with citations, never from memory.
  • Role-play (planned) - the AI plays user personas to stress-test requirements before anyone builds.

Hybrid retrieval (pgvector HNSW + Postgres full-text search, D63–D66) powers the connective tissue: duplicate detection in the belief layer (vector-only dedupe), chat answers grounded in cards and uploaded evidence, "does the uploaded material already answer this?", and evidence-aside questions with file provenance ([evidence:filename#chunk]). Vector and keyword channels are fused by reciprocal rank fusion; exact tokens ("Stripe", "70%") survive via FTS even when embeddings blur them. Cross-project organizational memory remains deferred.

Architecture

High-level design

Two deployables and a set of managed stores. The web app is one Next.js application; the backend is one FastAPI process that contains the REST API, the LangGraph agent runtime, and the background worker - a deliberate monolith for v1, split later only if load demands it. Everything external sits behind a port (a thin interface), which is what makes the free-tier hosts swappable for an on-prem box.

Key flows

Three flows explain the whole system

Ingestion - anything in, typed knowledge out

  1. Upload lands in R2; a job row is queued in Postgres; the API returns immediately.
  2. The worker picks it up: parse (documents) or transcribe via Whisper (audio), chunk with overlap (D64), embed into pgvector (768-dim, Gemini).
  3. Extraction proposes candidate facts, each strung supported-by to its exact chunk, with dual provenance (submitter and speaker).
  4. The belief layer compares candidates to known cards (indexed vector dedupe, meaning-first conflict scan): new → candidate card; duplicate → corroboration; contradiction → conflicts-with + review queue.
  5. The UI's coverage meters and "already answered" checks update from the same data.

Conversation - the interview loop

  1. A user message (or answered question card) reaches the LangGraph graph through the AG-UI endpoint.
  2. The graph reads the project model plus hybrid retrieval over cards and evidence (vector + keyword, RRF-fused on Postgres) — it skips areas uploads already cover and answers evidence asides with provenance labels.
  3. It replies with streamed text and A2UI widget payloads (question cards with their "why", conflict cards, coverage meters) chosen from our trusted catalog - the agent picks widgets, it cannot invent UI.
  4. Answers flow back through the same belief-layer path as any other input. Every turn is checkpointed, so a closed laptop resumes mid-interview.

Gate - how a phase actually ends

  1. Coverage rules from the phase template are satisfied (or explicitly N/A'd); the agent proposes gate readiness.
  2. The backend freezes an immutable snapshot of the relevant cards and renders the document view (Charter or SRS) from it - deterministically, no LLM.
  3. The graph hits a durable interrupt. The acceptance panel shows the snapshot; the human accepts or sends it back with reasons.
  4. Acceptance writes the audit record - name, timestamp, snapshot ID - and resumes the graph into the next phase, which inherits the accepted knowledge. Later changes to accepted ground raise change-impact flags; they never silently edit the snapshot.

Principles

Design rules that hold everywhere

  • Deterministic where it must be. Gates, document rendering, audit, traceability are plain code over typed data. LLMs draft and extract; they never decide or render.
  • One writer. All state changes go through the REST API; agent and worker call the same internal services. One code path to guard, one audit hook.
  • Everything behind ports. Model, embeddings, search, storage, transcription are config-swappable. No vendor-exclusive features, ever - migration to on-prem is compose-up, pg_dump, object sync, env vars.
  • One database. Queue, checkpoints, vectors, and domain data all live in Postgres until scale forces otherwise. One connection string, one backup, one local dev story.
  • Process as data. Phase definitions, coverage areas, gate rules, and view templates are versioned rows a project pins - not code.
Open before low-level design: ingestion format/size limits. Settled since this page was first written: the graph shape - one generic phase-runner per phase per project, gates as durable interrupts (D45-D48); single-user v1 (D43); and the physical schema - cards, strings, snapshots are real Postgres tables, snapshots hold pointers to card versions, not a document copy (D51-D52, see DECISIONS.md).
